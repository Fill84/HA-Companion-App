# Desktop registration without a hub entry

The Home Assistant integration is distributed through HACS, so its files are not automatically loaded by `default_config` like the built-in Mobile App integration. The first desktop must create a real config entry before the custom integration can run at HA startup. A permanent empty hub entry and an "Add hub" action are misleading.

The desktop now uses Home Assistant's administrator-only config-flow API when the compatibility ping endpoint is absent. It starts the `desktop_app` user flow, submits its own device metadata and a random 64-character webhook ID, then registers and updates sensors through HA's built-in webhook route. The HA integration does not need to register a new HTTP route after startup; on subsequent HA starts its existing compatibility API is registered normally. Existing desktops keep their device and webhook IDs and use that compatibility API. A repeated first-registration attempt retrieves the same webhook ID from its existing entry rather than creating another device.

The manifest keeps the programmatic config flow but does not advertise it in HA's add-integration picker. A fresh HACS installation still requires an HA restart so HA discovers the custom component. The first desktop needs an administrator token because HA's config-flow HTTP endpoint requires administrator permission. An absent or insufficient token must yield a clear error without changing an existing entry.

For upgrades, install the integration code first and confirm existing devices continue sending updates. Install the matching desktop build on both Windows test hosts. Back up HA config entries, entity registry and desktop settings; then remove only the legacy `is_hub` entry. Compare all existing device IDs, entity IDs and unique IDs before and after a HA restart, and verify fresh values from both desktops. Do not delete or recreate a device entry as part of this migration.

An isolated Home Assistant 2026.9.3 test on `render-unit` proved: no add-picker entry, zero hub entries, first and second device registration via HA's config-flow API, successful sensor webhook acknowledgements, persistence of both CPU sensor entity IDs after HA restart, restoration of the compatibility API after restart, and recovery of an existing webhook after an interrupted registration. This does not substitute for the live two-host upgrade checks.
